## gov · hana · hf 원본 평가 후보

**복합·고난도 확대 v2:** 기존 36쪽에 12개 소스 서식의 고난도 24쪽을 더한 48개 서식·60개 페이지 입력입니다. 근로·퇴직·연금소득 원천징수, 종합소득세 본표와 명세, 복합 금융 서식이 포함됩니다. [v2 후보](evalset/forms_candidates_v2/README.md)는 준비 워크플로가 테스트를 통과한 뒤 커밋합니다.

```bash
python -m http.server 8766 --bind 127.0.0.1 --directory evalset/forms_candidates_v2
```

선정 화면은 추가 고난도 24쪽부터 보여줍니다. 원본 PDF 페이지와 서식 안의 페이지를 구분하며, 같은 원본 계열은 family로 묶습니다. 다중 페이지 문서 전체 생성 평가가 아닌 페이지별 입력입니다. 기존 v1은 보존합니다. 재생성은 `build --selection evalset/selections/forms_complex_v2.json`으로 실행합니다. 기존 evaluate는 페이지 평균이므로 계열별 평균도 별도로 확인해야 합니다.


[원본 후보 36종](evalset/forms_candidates_v1/README.md)을 추가했습니다. 전체 502개 서식의 출처·동일 계열을 조사하고 gov 12·hana 12·hf 12종의 단일 페이지 원본 PDF를 입력 이미지로 준비했습니다. **최종 선정 전이며 기준 HTML은 아직 없습니다.**

로컬에서 `evalset/forms_candidates_v1/index.html`을 열어 채택/보류/제외를 기록하고 JSON으로 저장하세요. 원본 선정과 템플릿 승인은 별도 단계입니다. 자세한 절차는 후보 폴더 README에 있습니다.

재생성에는 `pip install -r requirements-data.txt` 후 다음 명령을 사용합니다. 출력 폴더를 덮어쓰지 않으므로 새 이름을 지정하세요.

```bash
python tools/prepare_form_candidates.py build --source ../document_gen --out evalset/forms_candidates_new
```

## 정답 라벨 (평가 재료)
평가 세트와 후보 60쪽의 항목마다 `labels.json`: 원본 이미지의 글자(고정 문구 / 값)·선·기재란·그림 자리와 위치. 평가 때 OCR 없이 이것과 맞춰 본다.
형식·출처·정확도는 [evalset/LABELS.md](evalset/LABELS.md), 만드는 법은 `tools/build_labels.py`. PDF 가 있는 항목은 PDF 에서 정확히, 없는 4개는 OCR 위치 + 기준 꾸러미 글자로 만들었다. 사람이 검수하지 않았다.

## 사람 검수 기준으로 모델 비교하기 (추가)

프론티어 모델이 만든 기준을 사람이 승인하고, 같은 값 변경 시험으로 모델들을 비교합니다.

```bash
pip install -r requirements.txt
python -m playwright install chromium
python -m tplgen review evalset/v1                       # 원본·기준·변경 시험 확인 → 승인
python -m tplgen bench configs/local.json                # 모델 생성 (기존 흐름)
python -m tplgen evaluate --dataset evalset/v1 --runs runs/exp1 --out out/exp1-reviewed
```

`--runs`는 설정의 `out`과 맞추세요. 뷰어는 `http://127.0.0.1:8765`입니다. `review ... --runs runs/exp1`로 모델 결과도 볼 수 있습니다. 승인된 기준이 바뀌면 재검수를 요구합니다. **기존 9개 기준은 아직 사람 승인되지 않았습니다.** 기존 `bench` 점수는 종전의 진단 지표이고, 승인 기준 점수는 별도의 `evaluate` 보고서입니다.

[검수·평가 사용법과 지표 정의](docs/review-evaluation.md)에 데이터 형식, 수동 필드 매핑, 비용 집계, 알려진 한계를 설명했습니다.

## 왜
업무 중 들어오는 문서(은행 서식, 기관·정부 문서, 스캔·사진)를 사람이 라벨링해 KIE·문서분류 모델을 만드는 수고를 줄인다.
문서 이미지 한 장을 **수정 가능한 템플릿**으로 바꿔 두면, 값과 표 행을 바꿔 가며 **라벨이 붙은 문서 이미지를 자동으로 대량 생성**할 수 있다.

## 누가 무엇을
| 누가 | 넣는 것 | 받는 것 |
|---|---|---|
| 사용자 | 문서 이미지 1장 | **템플릿 꾸러미** (아래) |
| 외주·다른 사람 | 꾸러미 + 값(json). 값은 파이썬이나 LLM 으로 만든다 | 문서 이미지 N장 + 라벨(어느 위치에 무슨 값) |

## 템플릿 꾸러미
```
<꾸러미>/
  template.html   문서의 틀 (Jinja2). 값은 {{ 이름 }}, 반복되는 표 행은 {% for %}. 값마다 data-field 로 위치를 알 수 있게 감싼다
  schema.json     들어가는 값의 목록: 항목(fields) · 반복 표(tables) · 종류
  sample.json     원본 이미지의 내용대로 채운 예시 값
```
규칙은 [`tplgen/prompts/template_v1.md`](tplgen/prompts/template_v1.md) 가 전부다 (모델에 주는 지시문이 곧 규격).
표 행은 값 목록의 길이만큼 늘고, 아래 내용은 저절로 밀린다 — 그래서 SVG 가 아니라 HTML 이다.

## 쓰는 법
```bash
# 1) 이미지 → 꾸러미 (모델 + 셀프 고치기 루프). 설정은 configs/example.json 을 복사해 고친다
python -m tplgen make --config configs/local.json --name model_a --image evalset/v1/hf153/image.png --out out/hf153

# 2) 꾸러미 + 값 → 이미지 + 라벨
python -m tplgen render out/hf153/final --data my.json --out gen/0001        # 0001.png, 0001.json
python -m tplgen vary   out/hf153/final --n 20 --out gen/                    # 값을 임의로 바꿔 20장

# 3) 꾸러미가 쓸 만한가 (정답 없이 잰다)
python -m tplgen check out/hf153/final --image evalset/v1/hf153/image.png

# 4) 여러 모델 × 평가 세트(난이도 하·중·상) 비교
python -m tplgen bench configs/local.json        # 길 검사: configs/reference.json → 9/9
```

## 잘 만들었는지 재는 법 (`check`)
정답 파일 없이, **꾸러미를 실제로 돌려 보고** 잰다.

| 점수 | 뜻 |
|---|---|
| 유효 `valid` | 규칙대로이고 예시 값으로 그려지는가 |
| 자리 재현 `coverage` | 평가 세트에서만: 기준 꾸러미의 값 자리 중 같은 자리에 값 자리를 만든 비율. 원본 값을 고정 글자로 박고 값 자리를 거의 안 만든 '게으른' 꾸러미를 잡는다 (기준 샘 `ref_leak` 도 같이) |
| 빠짐 `missing` | 원본에서 통째로 빠진 가장 큰 덩어리가 원본 잉크의 몇 할인가 (0~1). 닮음은 평균이라 표 하나가 빠져도 0.7 이 나올 수 있어서 따로 본다 |
| 닮음 `layout` | 예시 값으로 그린 그림과 원본이 위에서 아래로 같은 모양의 줄을 같은 순서로 갖는 정도 (0~1). 글꼴·행 높이·여백 차이는 봐주고, 사진은 종이 부분만 잘라 비교하며, 그림 자리(바코드 등)는 채워진 것으로 본다 |
| 견딤 `robust` | 값을 바꾸고(짧게·길게) 표 행을 바꿔(0·1·많이) 그려도 깨지지 않는 비율. 깨짐 = 넘침·겹침·값 누락·행 수 불일치 |
| 샘 `leak` | 예시 값이 틀에 고정 글자로 박혀 있는 수 (0 이어야 함) |
| 자리 수 | 항목·표·표의 열 개수 (참고) |

**쓸 만함(임시 기준) = 유효 ∧ 견딤 = 1 ∧ 샘 = 0 ∧ 닮음 ≥ 0.6 ∧ 빠짐 ≤ 0.12 ∧ (평가 세트에서) 자리 재현 ≥ 0.7 ∧ 기준 샘 = 0.** `tplgen/check.py` 의 `PASS_RULE`.

## VLM 모델별 생성 성능을 잴 때
```bash
cp configs/example.json configs/local.json     # 모델 주소·이름·vLLM 옵션을 채운다. "images": "evalset/v1", "rounds": 2
python -m tplgen bench configs/local.json      # → runs/<out>/compare.md : 모델 × (한 번만 생성 / 고치기 뒤) × 하·중·상
```
- **루프가 회차를 고를 때는 기준 꾸러미를 쓰지 않는다.** 기준 꾸러미는 채점에만 쓴다 (정답이 루프에 새면 고치기 효과가 부풀려진다).
- 모델에 필요한 것: 이미지 입력, 한 번에 세 파일(HTML·JSON 둘)을 이어 쓰는 출력. 기준 꾸러미 길이로 어림하면 항목마다 출력 2천~5천 토큰 (W-9 가 가장 길다). 고치기 회차는 입력에 이미지 2장과 직전 파일 전체가 들어간다.
- 이렇게 읽는다: **전체 쓸 만함**(9장 중 몇 장)으로 모델을 거르고, 난이도 칸으로 어디서 무너지는지 본다. 닮음 평균 차이 0.05 미만은 같은 것으로 본다 (점수와 눈 실험).
- 9장뿐이라 한 장 차이(11%p)는 우연일 수 있다. 온도 > 0 이면 같은 설정으로 두세 번 돌려(`out` 을 바꿔) 흔들림을 본다.
- 실패 유형은 각 결과 폴더의 `results.jsonl` (`issues`, `broken_tests`) 과 `round<k>/tests/*.png` 그림으로 본다.

## 점수와 눈이 맞는가
문서 3종(hf153 · IRS 8949 · 비스듬한 인보이스)의 꾸러미를 7가지로 바꿔 그리고, **점수를 보기 전에** 큰 모델이 그림만 보고 원본에 가까운 순서를 적은 뒤 점수와 맞춰 봤다 (그림은 섞고 A~G 로만 표시).

| 눈 순위 | hf153 | IRS 8949 | 인보이스 사진 |
|---|---|---|---|
| 1 | 간격 벌림 0.79 / 0.04 통과 | 그대로 0.86 / 0.00 통과 | 그대로 0.72 / 0.04 통과 |
| 2 | 그대로 0.83 / 0.04 통과 | 글자 축소 0.74 / 0.03 통과 | 글자 축소 0.74 / 0.04 통과 |
| 3 | 글자 축소 0.66 / 0.07 통과 | 간격 벌림 0.87 / 0.01 통과 | 간격 벌림 0.68 / 0.05 통과 |
| 4 | 표 빠짐 0.70 / 0.16 탈락 | 표 빠짐 0.53 / 0.23 탈락 | 표 빠짐 0.59 / 0.35 탈락 |
| 5 | 순서 뒤집힘 0.49 / 0.19 탈락 | 순서 뒤집힘 0.60 / 0.08 탈락 | 순서 뒤집힘 0.52 / 0.07 탈락 |
| 6 | 글자 지움 0.49 / 0.21 탈락 | 글자 지움 0.53 / 0.32 탈락 | 글자 지움 0.07 / 0.80 탈락 |
| 7 | 다른 문서 0.38 / 0.05 탈락 | 다른 문서 0.28 / 0.35 탈락 | 다른 문서 0.32 / 0.20 탈락 |

칸 = 닮음 / 빠짐. 눈 순위와 닮음 순위의 상관(스피어만) 0.89 · 0.86 · 0.93.
- **맞는 것**: 통과/탈락의 경계가 세 문서 모두 눈과 같다 — 다 있는 것(3위까지)은 통과, 무언가 빠지거나 뒤집히거나 다른 문서면 탈락.
- **처음엔 틀렸던 것**: 닮음만 있을 때 hf153 의 **표가 빠진 것이 0.70 으로 통과**했다. 줄마다 잉크 양으로 무게를 주는 안은 오히려 셋 다 통과시켜 버려서 버렸고, '빠짐' 을 따로 재서 잡았다.
- **못 가리는 것**: 위쪽 세 개(그대로 · 글자 축소 · 간격 벌림) 사이의 순서. 세로 간격은 일부러 안 보므로 간격이 벌어져도 점수가 같거나 높다. 그 차이는 눈으로도 헷갈렸다 (hf153 에서 1·2위를 반대로 골랐다). 즉 **점수는 '쓸 만한가'를 가리는 데 쓰고, 통과한 것끼리의 미세한 순위로는 쓰지 않는다.**
- 아슬아슬한 것: 8949 의 순서 뒤집힘이 0.599 로 겨우 탈락. 시험한 변형이 21개뿐이다.

## 지금 상태
| | |
|---|---|
| 확인함 | 점수가 망가진 꾸러미를 잡는가 (`tests/`): 값이 틀에 박힘 → 샘, 표 폭 고정 → 넘침, 칸 높이 고정 → 잘림, 행이 안 늘어나는 표 → 값 누락, 본문 빠짐 → 닮음 하락 |
| 확인함 | 닮음 점수의 기준점 (hf153): 같은 문서 0.8 안팎 · 스캔본 0.76 · **전혀 다른 문서 0.4 안팎**. 처음 쓴 방식(잉크 위치를 그대로 겹침)은 다른 문서와도 0.6 이 나와 버렸다 |
| 고친 것 (모델 비교 전 점검) | **게으른 꾸러미가 통과하던 것**: 원본 값을 고정 글자로 박고 값 자리를 하나만 둔 꾸러미가 hf153 · 인보이스 사진 · W-9 에서 모두 '쓸 만함' 이었다 (닮음·견딤이 높게 나옴) → 기준 꾸러미와 견주는 자리 재현·기준 샘을 더해 셋 다 탈락. 기준 꾸러미끼리는 자리 재현 1.0 |
| 확인함 | 루프: 고쳐서 나아지면 뒤 회차를, 고치다 망가지면 앞 회차를 final 로 고름 |
| 고친 것 (복잡한 문서 시험에서) | **평가**: 비스듬히 찍은 사진은 종이를 네모로만 자르면 배경과 기울기가 남아 맞는 꾸러미도 0.26 → 종이의 네 모서리를 찾아 펴서 비교 (0.59, 고친 뒤 0.72). 영수증 사진도 0.66 → 0.77 |
| 고친 것 | **값 만들기**: 영어 문서에 한국어 값이 들어감 → schema 의 `language`. 날짜·금액 꼴이 원본과 다름 → `format` (`DD/MM/YYYY`, `R # ###,##`, `###-##-####`) |
| **아직 안 함** | **실제 vLLM 모델로 돌리기** — 작은 VLM 이 세 파일 형식을 지키는지, 출력 길이(최대 5천 토큰 안팎)를 버티는지부터 본다 |
| 알고 쓸 것 | 자리 재현은 **기준 꾸러미의 판단**(무엇을 값으로 뺐나)에 기댄다. 기준은 큰 모델 하나가 쓴 것이라, 다르게 판단한 모델이 손해를 볼 수 있다 (그래서 기준을 0.7 로 느슨하게 둠) |
| **아직 안 함** | 닮음 점수가 사람 눈과 맞는지. 같은 문서/다른 문서는 가르지만 **작은 차이에는 둔하다** (영수증에서 줄 넘김을 고쳐도 0.66 그대로). 0.05 보다 작은 차이는 오차로 본다 |
| **아직 안 함** | 사람이 스캐너로 뜬 실제 스캔본, 여러 쪽 문서, 심하게 기운 사진 (기울면 닮음이 내려간다: 1.2° 에 0.86 → 0.76) |
| 모르는 것 | 사내에서 HTML 그리기 — Playwright Chromium 을 도커에 넣어 쓸 예정 |
| 재지 않는 것 | **값끼리 맞는가**: 합계가 품목 합과 다르고, 만기일이 발행일보다 앞설 수 있다. 칸의 뜻까지 맞는 값은 schema.json 을 LLM 에 주고 만들게 해야 한다 |
| 재지 않는 것 | 값이 아닌 글자끼리 겹침 · 쪽 나눔(행이 많으면 한 장이 길어진다) · 만든 이미지를 스캔·사진처럼 만드는 것(`tools/scanify.py` 가 시작점) |
